MODULE 01

Introduction to Airflow & Architecture

TL;DR
Airflow is workflow orchestration as Python code — it decides when tasks run and in what order, but it doesn't process data itself (Spark, dbt, or your Python script does the actual work). Five moving parts: the Scheduler (decides what runs next), the Webserver (UI), the Executor (decides where/how a task runs — locally, via Celery workers, via Kubernetes pods), the Metadata DB (single source of truth for every DAG's state), and the Triggerer (runs async/deferred sensors without blocking a worker slot). Everything reads and writes through the metadata DB — that's why the UI is never the source of truth, it's just a window into it.

ARCHITECTURE DIAGRAM

Scheduler parses DAG files and writes DagRuns/TaskInstances to the metadata DB → Executor asks the DB what's ready and hands it to a Worker → Worker writes results back to the DB → Webserver only ever reads the DB. Deferred sensors hand off to the Triggerer so they don't tie up a worker slot while waiting.

CODE — MINIMAL DAG SKELETON

# every DAG file needs these three things: an import, a DAG object, and at least one task
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime

def hello():
    print("Airflow only decides WHEN this runs, not HOW it runs internally")

with DAG(
    dag_id="architecture_demo",
    start_date=datetime(2026, 1, 1),
    schedule="@daily",
    catchup=False,
) as dag:
    PythonOperator(task_id="hello", python_callable=hello)

INTERVIEW Q&A

SHORTWhat is Apache Airflow, in one sentence?

A platform to author, schedule, and monitor workflows defined as Python code, where each workflow is a DAG (directed acyclic graph) of tasks.

SHORTAirflow vs a cron job — why does the difference matter?

Cron only knows "run this at this time." It has no idea if the previous run failed, no dependency graph between scripts, no retry logic, no UI, and no shared state between steps. Airflow adds all of that: dependency-aware scheduling, retries, alerting, a UI to see history, and a way to pass small values between tasks (XCom).

SHORTName the Airflow executors and one line on each.

LocalExecutor — runs tasks as parallel processes on the same machine as the scheduler; fine for small setups. CeleryExecutor — distributes tasks to a pool of pre-running worker machines via a message queue (Redis/RabbitMQ); scales horizontally, workers are always on. KubernetesExecutor — spins up a fresh pod per task and tears it down after; scales to zero, better isolation, slightly higher per-task startup latency.

LONGWalk me through exactly what happens between a DAG being scheduled and a task instance turning green in the UI.

Break it into four hops, because that's how interviewers actually check you understand the architecture instead of having memorised a diagram:

1. Parse: the Scheduler continuously scans the DAGs folder, re-parses each Python file, and builds an in-memory DAG object.

2. Schedule: once a DAG's schedule condition is met, the Scheduler creates a DagRun and one TaskInstance per task, writing them to the Metadata DB in a "scheduled" or "queued" state.

3. Execute: the Executor picks up queued TaskInstances and hands them to a Worker (a process, a Celery worker, or a new K8s pod depending on which executor is configured). The worker runs the actual `python_callable` or operator logic and streams logs.

4. Report: when the task finishes, the worker writes the final state (success/failed) back to the Metadata DB. The Webserver is just reading that same DB on a refresh — it never talks to the worker directly.

Say it like: "Scheduler decides what should run and writes it to the DB, the executor decides where it runs and hands it to a worker, the worker does the actual work and writes the result back, and the UI is just a live read of that same database."

LONGWhy is the Metadata DB described as the "single source of truth," and what breaks if it goes down?

Every component — Scheduler, Executor, Workers, Webserver — reads and writes state through that one database instead of talking to each other directly. That's a deliberate design choice: it decouples the components so any of them can restart or scale independently without losing state, because nothing is held in memory that isn't also persisted.

If it goes down: the Scheduler can't create new DagRuns or mark tasks as queued, the Webserver shows stale or no data, and in-flight tasks that are mid-execution may finish but be unable to report their final state back — so you'd see tasks stuck in "running" even after they've actually completed on the worker. This is also why Airflow's metadata DB is usually the first thing you'd put on a managed, highly-available database service in production rather than a single container.

SCENARIO

Your team currently runs 12 nightly ETL scripts via cron on a single EC2 box. One engineer is the only person who knows which script depends on which, and failures are only discovered when a downstream report is empty the next morning. You're asked to propose moving this to Airflow.

How to structure the answer: Don't jump to code — walk the architecture first. (1) Model the 12 scripts as one or more DAGs with explicit `>>` dependencies, so the tribal knowledge becomes visible in a Graph view. (2) Pick an executor: LocalExecutor is enough for 12 sequential-ish jobs; only justify Celery/Kubernetes if you expect this to grow to dozens of concurrent DAGs. (3) Turn on retries and failure alerting (email/Slack) so failures surface in minutes, not the next morning. (4) Point out that the Metadata DB now gives you a queryable audit trail of every run — something cron never had.

BUSINESS / CLIENT CASE

CLIENT SAYS

"Our nightly finance reports fail silently a couple of times a month, and we only find out when someone in the business team complains that numbers look wrong. We don't even know how often this actually happens."

How you'd respond: This is an observability and alerting problem, not a compute problem — and it's exactly what Airflow's architecture is designed to fix. Every run is persisted in the Metadata DB, so you get an audit trail (how often does this actually fail, and where) instead of anecdotal complaints. Layer on `on_failure_callback` or a Slack/email alert so the team is notified within minutes, not weeks. Frame the value in business terms: this converts "silent, undetected data quality risk" into "detected within minutes, with a full history to diagnose root cause."

MODULE 02

DAGs, Operators & Task Dependencies

TL;DR
A DAG is the workflow definition; a task is one node in it, created by an Operator (Bash, Python, SQL, Spark...) which is a reusable template for "what kind of work." Dependencies (>>) define order. Branching (BranchPythonOperator) lets one path of the DAG run instead of another based on logic — ShortCircuitOperator is the simpler cousin: it just skips everything downstream if a condition is false, no picking between paths. TaskGroups are purely a UI/organisation tool (no execution semantics) for collapsing a cluster of tasks visually. Sensors wait for something external (a file, a table, another DAG) before letting the DAG proceed.

ARCHITECTURE DIAGRAM — BRANCHING DAG

This is the exact pattern from your order-validation DAG. The dashed arrow into close_kitchen is the one people forget: without `trigger_rule="none_failed"`, close_kitchen inherits the default `all_success` rule and silently skips forever whenever raise_alert's branch fires.

CODE — BRANCHING + TASKGROUP

from airflow.operators.python import BranchPythonOperator
from airflow.operators.empty import EmptyOperator
from airflow.utils.task_group import TaskGroup

def check_total(**context):
    total = context["ti"].xcom_pull(task_ids="sum_orders")
    if total is None:
        raise ValueError("sum_orders pushed nothing to XCom")
    return "raise_alert" if total < 100 else "merge_and_write"

# TaskGroup is UI-only sugar — it does not change execution order,
# it just collapses these tasks into one node in the Graph view
with TaskGroup(group_id="validation") as validation:
    check = BranchPythonOperator(task_id="check_total", python_callable=check_total)
    raise_alert = EmptyOperator(task_id="raise_alert")
    merge_and_write = EmptyOperator(task_id="merge_and_write")
    check >> [raise_alert, merge_and_write]

INTERVIEW Q&A

SHORTBranchPythonOperator vs ShortCircuitOperator — what's the actual difference?

BranchPythonOperator picks which one of several downstream paths to run — it returns a task_id (or list of task_ids). ShortCircuitOperator is binary: it returns True/False, and if False, everything downstream of it is skipped entirely — there's no "other path," just "continue or stop."

SHORTWhat's the difference between a Sensor and a normal task waiting via `time.sleep`?

A Sensor is built for polling — it retries checking a condition (file exists, row count matches, another DAG finished) on an interval, and importantly it can run in "reschedule" mode, which frees up the worker slot between checks instead of blocking it, unlike a task that just sleeps inside its own process.

SHORTAre SubDAGs still recommended?

No — SubDAGs are deprecated in modern Airflow because they had serialization and deadlock issues. TaskGroups replaced them for visual grouping, since TaskGroups don't spin up a separate DAG run.

LONGExplain "poke" mode vs "reschedule" mode for sensors, and when you'd pick each.

Poke mode holds onto the worker slot for the entire waiting period — it checks the condition, and if not met, just sleeps and checks again, all inside the same process. This is fine for short waits, but if you have many sensors waiting a long time, you can exhaust your worker pool with tasks that are doing nothing but waiting.

Reschedule mode releases the worker slot between checks and re-queues itself, so the slot is available for other tasks while this one is "waiting." You'd pick reschedule mode for anything that might wait more than a few minutes — e.g. waiting for a file that could land anywhere from 5 minutes to 3 hours late.

Say it like: "Poke blocks a worker the whole time it's waiting; reschedule frees the worker between checks — so for long or unpredictable waits, reschedule mode, or better, a deferred sensor via the Triggerer, is the production-safe choice."

LONGYou inherited a DAG where a downstream "send_notification" task keeps getting skipped forever whenever the pipeline hits an error branch. Diagnose it.

This is almost always a trigger_rule issue. By default, every task uses `all_success` — meaning it only runs if every direct upstream task succeeded. When you have a BranchPythonOperator, the branch that wasn't chosen is marked skipped, not failed or successful — and a skip propagates downstream by default, so any task depending on both branches (like a final notification step) inherits that skip and never runs.

The fix is setting `trigger_rule="none_failed"` (run as long as nothing upstream actually failed — skips are fine) or `trigger_rule="none_failed_min_one_success"` if you want to require at least one real success. This is precisely the `close_kitchen` pattern from Module 2's diagram.

How to structure the answer: extract → BranchPythonOperator(validate) → [alert_team, load_warehouse] → pipeline_complete with `trigger_rule="none_failed"`. Mention explicitly that pipeline_complete needs the non-default trigger rule, because that's the detail that separates someone who's built this before from someone reciting operator names.

CLIENT SAYS

"Twice last quarter, corrupted vendor data got loaded straight into our warehouse and broke downstream dashboards before anyone noticed."

How you'd respond: The root cause is almost certainly a missing validation gate — the pipeline probably goes straight from extract to load with no branch in between. Frame it for a non-technical stakeholder as: "we're adding a checkpoint that stops bad data at the door instead of finding it after it's already in the dashboard."

MODULE 03

Scheduling, Triggers & Backfill

TL;DR
Airflow schedules runs for a completed data_interval, not the moment you'd naively expect — a `@daily` DAG for Jan 1 actually runs at the start of Jan 2, once the Jan 1 interval has fully passed. That timestamp is the logical_date (the old, confusing name was `execution_date`). catchup=True (default) will backfill every missed interval since `start_date` the moment you deploy — a common footgun. Datasets let a DAG trigger based on another DAG producing data, instead of a blind time-based sensor. Retries + retry_delay (+ exponential backoff) handle transient failures without paging a human.

DIAGRAM — LOGICAL DATE VS DATA INTERVAL

This is the single most common source of "why is my date off by one day" confusion in interviews and in production. The interval has to close before Airflow will run the task for it.

CODE — RETRIES & DATASET-TRIGGERED DAG

from airflow import DAG, Dataset
from airflow.operators.python import PythonOperator
from datetime import datetime, timedelta

orders_dataset = Dataset("s3://bucket/orders/daily/")

# producer DAG: writes to the dataset URI when it succeeds
with DAG("produce_orders", start_date=datetime(2026,1,1), schedule="@daily", catchup=False) as dag:
    PythonOperator(
        task_id="write_orders",
        python_callable=lambda: None,
        outlets=[orders_dataset],
        retries=3,
        retry_delay=timedelta(minutes=5),
        retry_exponential_backoff=True,
    )

# consumer DAG: triggers automatically once orders_dataset is updated —
# no time-based schedule, no ExternalTaskSensor polling loop needed
with DAG("consume_orders", start_date=datetime(2026,1,1), schedule=[orders_dataset], catchup=False) as dag2:
    PythonOperator(task_id="process", python_callable=lambda: None)

INTERVIEW Q&A

SHORTWhy does a `@daily` DAG show "Jan 1" but actually run on Jan 2?

Because Airflow schedules for a completed interval. The Jan 1 interval only "closes" at midnight Jan 2, and that's when the scheduler actually triggers the run — the label just refers to the interval it's processing, not the moment it executed.

SHORTWhat's the risk of deploying a new DAG with `catchup=True` and a `start_date` from a year ago?

Airflow will immediately try to backfill every missed daily (or whatever interval) run since that start_date — potentially hundreds of DagRuns firing at once, overwhelming the executor/workers and, if the task hits an external API or database, potentially rate-limiting or overloading it too.

SHORTDatasets vs ExternalTaskSensor — when would you use each?

Datasets are push-based and declarative — the producer DAG declares it writes to a Dataset, and consumers auto-trigger on that update, no polling. ExternalTaskSensor is pull-based — the consumer DAG actively polls for another DAG's specific task to reach a certain state. Datasets are the more modern, lower-overhead choice when you control both DAGs; ExternalTaskSensor still has a place for tighter coupling on exact task-level state within a run.

LONGA junior engineer deploys a DAG with `start_date=datetime(2024,1,1)` and forgets to set `catchup=False`. It's now 2026. Walk through what happens and how you'd handle it.

The moment that DAG is unpaused, the Scheduler sees roughly 730+ missed daily intervals between the start_date and now, and — because `catchup` defaults to True — it queues a DagRun for every single one of them. Depending on the executor's parallelism settings, this can flood the worker pool, spike load on any external system the task hits (API, database), and make the UI genuinely hard to read because it's buried under two years of backfill runs.

Immediate fix: pause the DAG, then either delete the unwanted DagRuns via the UI/CLI or use `airflow dags backfill` selectively if some historical runs are actually wanted, then set `catchup=False` and un-pause.

Prevention: this should be caught in code review or a CI lint step — a new DAG's `start_date` should almost always be recent, and `catchup` should be explicit rather than left to default, precisely because the default is the dangerous option.

PROJECT-BASED SCENARIO

SCENARIO

Pipeline B (sales aggregation) must only run after Pipeline A (raw order ingestion) has actually landed fresh data — not just "some time after," because A's landing time varies by 20 minutes to 4 hours daily.

How to structure the answer: A time-based schedule on B is the wrong tool here because A's completion time isn't fixed. Use Datasets: A declares an `outlets=[orders_dataset]` on its final task, and B's DAG uses `schedule=[orders_dataset]` instead of a cron string — B fires automatically and only when A actually finishes, regardless of what time that happens to be.

BUSINESS / CLIENT CASE

CLIENT SAYS

"Our finance dashboard sometimes shows numbers computed from yesterday's data instead of today's, and we don't understand why — the pipeline is scheduled correctly."

How you'd respond: This usually traces back to the logical_date vs data_interval gap, or a fixed-time schedule racing against an upstream source that doesn't land on a fixed schedule. Ask when the upstream data actually lands each day — if it varies, a rigid cron schedule will sometimes run before the day's data has arrived. Recommend switching the downstream DAG to a Dataset-triggered schedule so it only ever runs after the upstream data is confirmed present, removing the race condition entirely.

MODULE 04

Web UI, CLI & Monitoring

TL;DR
Grid view = history across runs (your main daily-check screen). Graph view = dependency structure of one run. Gantt = where time is actually being spent (spot bottlenecks). Calendar = success/failure at a glance over weeks/months. "Clear" re-queues a task to run again; "Mark Success/Failed" just changes the recorded state without re-running anything — know the difference before you click either in production. The CLI (`airflow tasks test`, `airflow dags list-import-errors`, etc.) is how you debug without waiting on the scheduler. Logs should go to remote storage (S3/GCS/CloudWatch) in production, not local disk, or you lose them when a worker/pod is recycled.

DIAGRAM — DEBUGGING A STUCK TASK

This is the sequence to say out loud in an incident-response interview question — logs first, then queue/executor, then worker health, then decide whether to clear (retry) or escalate.

CODE — CLI DEBUGGING

# run ONE task in isolation, ignoring dependencies — the fastest way to test task logic
airflow tasks test architecture_demo hello 2026-01-01

# catch DAG import errors before they silently vanish from the UI
airflow dags list-import-errors

# list every DAG the scheduler currently sees
airflow dags list

# manually trigger a DAG run right now, outside its schedule
airflow dags trigger architecture_demo

INTERVIEW Q&A

SHORT"Clear" vs "Mark Success" — what's the practical difference?

Clear removes the task instance's state and re-queues it to actually run again. Mark Success just flips the recorded state to success without executing anything — useful when you've fixed the underlying data manually and don't want the task to redo work, but dangerous if used to "make the red go away" without actually understanding why it failed.

SHORTGrid view vs Gantt view — when do you reach for each?

Grid view for "has this DAG been healthy over the last N runs" — your daily glance. Gantt view for "which specific task is eating all the time in this one run" — your bottleneck-finding tool when a DAG that used to finish in 20 minutes now takes 2 hours.

SHORTWhy should production logs go to S3/GCS/CloudWatch instead of local disk?

Workers (especially with KubernetesExecutor, where each task gets a fresh pod) are ephemeral — once the pod is torn down, anything written only to its local disk is gone. Remote logging keeps logs available after the compute that produced them no longer exists, which is also usually a compliance/audit requirement.

LONGA task has been running for 3 hours in production when it usually takes 15 minutes. Walk through your debugging steps.

1. Logs first. Open the task's logs in the UI (or the remote log store if the UI is slow). Is it actually doing work — progressing through log lines — or stuck at one line, which suggests a hang (e.g. waiting on a lock, an API call with no timeout)?

2. Check queue depth / executor. If logs show nothing running yet, it may not have even started — check whether it's stuck in "queued" because the executor's worker pool is saturated by other tasks.

3. Check worker health. Is the worker (or pod, if KubernetesExecutor) actually alive — CPU/memory not maxed out, no OOM kill in its history?

4. Decide: wait, clear, or kill. If it's a known slow-but-safe query, let it finish. If it's genuinely hung, clear the task (which kills and re-queues it) rather than letting it block downstream tasks and SLA alerts indefinitely.

Say it like: "I'd check logs first to see if it's actually stuck or just slow, then check whether the bottleneck is upstream — queue or worker capacity — before deciding whether to let it run, clear it, or escalate."

SCENARIO

Set up failure alerting so the on-call engineer is pinged in Slack within 2 minutes of any production DAG failing, without them having to keep the Airflow UI open all day.

How to structure the answer: Add an `on_failure_callback` at the DAG or `default_args` level that posts to a Slack webhook (or use the `SlackWebhookOperator`/`SlackNotifier`). MODULE 05

XComs, Variables, Connections & Templating

TL;DR
XCom passes small values between tasks through the metadata DB — never pass a dataframe or a large file through it, only IDs, counts, small strings/dicts. Variables are global key/value config (like feature flags or thresholds) accessible from any DAG. Connections store credentials/endpoints for external systems, ideally never hardcoded in DAG code. Jinja templating (`{{ ds }}`, `{{ ti }}`, custom macros) lets operator parameters be computed at render time instead of at DAG-parse time. In production, Variables and Connections should be backed by a real secrets manager (AWS Secrets Manager, GCP Secret Manager, Vault), not the Airflow UI's built-in storage.

DIAGRAM — XCOM FLOW

Tasks never talk to each other directly — everything, including XCom, is mediated through the metadata DB. That's the same architectural principle from Module 1, applied to inter-task data passing.

CODE — XCOM, VARIABLE, CONNECTION, TEMPLATING

from airflow.models import Variable
from airflow.hooks.base import BaseHook
from airflow.operators.python import PythonOperator

def push_count(**context):
    context["ti"].xcom_push(key="row_count", value=4213)

def use_config(**context):
    # Variable: global config, e.g. a threshold you tune without redeploying code
    threshold = Variable.get("min_row_threshold", default_var=100)

    # Connection: credentials never hardcoded in the DAG file
    conn = BaseHook.get_connection("prod_postgres")

    row_count = context["ti"].xcom_pull(task_ids="push_count", key="row_count")
    if row_count < int(threshold):
        raise ValueError("row count below threshold")

push = PythonOperator(task_id="push_count", python_callable=push_count)
use  = PythonOperator(task_id="use_config",  python_callable=use_config)
push >> use

# Jinja templating example — {{ ds }} is resolved to the run's date string at RENDER time,
# not when the DAG file is parsed
# sql="SELECT * FROM orders WHERE order_date = '{{ ds }}'"

INTERVIEW Q&A

SHORTWhy shouldn't you push a pandas DataFrame through XCom?

XCom values are serialized and stored as rows in the metadata database. A DataFrame can be large, and stuffing it into the DB bloats the database, slows down every query against that table, and isn't what XCom was designed for — it's meant for small signalling values like a count, an ID, or a short status string. For passing actual datasets between tasks, write to shared storage (S3, a table, a file) and pass the path/reference through XCom instead.

SHORTVariable vs Connection — how do you decide which one to use?

Variable for general config values (a threshold, a feature flag, an environment name). Connection specifically for how-to-reach-an-external-system details — host, login, password, connection type — because Connections get special handling for credential masking and secrets backend integration that plain Variables don't.

SHORTWhat does `{{ ds }}` actually resolve to?

The DAG run's logical date formatted as YYYY-MM-DD — one of Airflow's built-in Jinja macros, resolved when the operator's templated fields are rendered, not when the Python file is parsed.

LONGHow would you securely manage a database password that's currently hardcoded in 20 different DAG files?

First, stop the bleeding: move the credential into an Airflow Connection instead of a string literal in code, so it's no longer sitting in plaintext in version control — anyone with repo access currently has the production password, which is the real risk here.

Second, for a genuinely production-grade setup, back that Connection with an external secrets manager (AWS Secrets Manager, GCP Secret Manager, or HashiCorp Vault) rather than Airflow's own metadata DB — Airflow supports pluggable secrets backends specifically for this, so the actual secret value never lives in Airflow's database at all, only a reference to where to fetch it.

Third, update all 20 DAGs to reference the Connection by `conn_id` via a Hook, and treat the old hardcoded password as compromised — rotate it, since it's been exposed in git history even after you remove it from the current file.

Say it like: "Move it out of code into a Connection first to stop it being in version control, then back that Connection with a real secrets manager so Airflow itself never stores the raw secret, and rotate the old password since it's already been exposed."

PROJECT-BASED SCENARIO

SCENARIO

The same DAG needs to run against a dev database in the dev environment and a prod database in prod, without maintaining two separate copies of the DAG file.

How to structure the answer: Use a Variable (e.g. `env_name`) or Airflow's built-in environment detection to pick which Connection ID to use at runtime — `conn_id = f"{Variable.get('env_name')}_postgres"`. This keeps one DAG file that's environment-agnostic, with the actual environment-specific details (credentials, hosts) living in Connections managed outside the code.

BUSINESS / CLIENT CASE

CLIENT SAYS

"Our security audit flagged that a production database password is sitting in plaintext inside a Python file in our Git repository."

How you'd respond: This is exactly the Connections + secrets backend fix above — walk them through moving the credential out of code into a Connection backed by a secrets manager, and stress that the old password must be rotated, not just removed from the current file, because Git history still has it. Frame it as a one-time migration plus a standing rule going forward: no credential is ever a string literal in a DAG file.

MODULE 06

CI/CD, Plugins & Dagster

TL;DR
Production Airflow deploys DAGs via git-sync (a sidecar/process continuously pulling the DAGs repo) rather than manual file copying. CI/CD (GitHub Actions/Jenkins) should lint and import-check DAGs before merge, so a broken DAG never even reaches the scheduler. Auth in production goes through OAuth/OIDC/LDAP, not the default local user store. Dagster is a newer, competing orchestrator built around software-defined assets (the data itself, and its lineage, is the first-class concept) rather than Airflow's task-centric model (the code that runs is the first-class concept) — Dagster tends to win on built-in observability/testing for asset-heavy platforms; Airflow wins on ecosystem maturity, provider integrations, and hiring pool size.

DIAGRAM — CI/CD DEPLOYMENT FLOW

The whole point of the CI step is that a DAG with a Python import error never reaches production — it fails the PR instead of silently vanishing from the Airflow UI (which is what happens when the scheduler can't parse a file).

CODE — CI CHECK FOR DAG IMPORT ERRORS

# .github/workflows/dag-check.yml (conceptual step)
# fails the PR if any DAG file can't be imported/parsed cleanly
- name: Validate DAGs
  run: |
    python -m pip install apache-airflow
    airflow db init
    airflow dags list-import-errors --output json > errors.json
    if [ "$(cat errors.json)" != "{}" ]; then
      echo "DAG import errors found:"; cat errors.json; exit 1
    fi

INTERVIEW Q&A

SHORTWhat is git-sync and why use it over manually copying DAG files?

git-sync is a sidecar process that continuously pulls the latest commit from a DAGs repository into the scheduler/webserver's DAGs folder. It removes the human-in-the-loop deployment step (someone SCPing files), makes deployment auditable through Git history, and means every environment is running exactly what's in a known commit.

SHORTIn one sentence, what's the core philosophical difference between Airflow and Dagster?

Airflow is task-centric — "run this code, in this order"; Dagster is asset-centric — "produce this data asset, and track its lineage, freshness, and quality," with the pipeline code as a means to that end rather than the primary unit of thought.

SHORTWhat's the quickest way to catch a broken DAG before it reaches production?

A CI step that runs `airflow dags list-import-errors` (or simply tries to import each DAG file) against the PR branch, failing the build if any DAG can't be parsed — catching it in code review instead of discovering it later as a DAG that's mysteriously absent from the UI.

LONGYour company is evaluating Dagster vs Airflow for a brand-new data platform. How do you advise them?

Ask what they're optimising for first — this isn't a "which is better" question, it's a fit question.

Lean Airflow if: they need the widest possible library of pre-built integrations (providers for practically every cloud/SaaS tool), a large existing hiring pool with Airflow experience, or they're integrating into an org that already runs Airflow elsewhere.

Lean Dagster if: the team thinks primarily in terms of data assets and lineage (e.g. a data platform team building a catalog of curated tables/ML features), wants strong built-in testing and local development ergonomics, or is starting fresh with no legacy Airflow DAGs to migrate.

In practice, also weigh switching cost — if the org already has hundreds of Airflow DAGs in production, the migration cost to Dagster usually has to be justified by a very specific pain point Airflow isn't solving, not just "Dagster is newer."

Say it like: "It depends on whether they think in tasks or assets, and how much existing Airflow investment they'd be walking away from — I wouldn't recommend a rewrite just because Dagster is newer."

PROJECT-BASED SCENARIO

SCENARIO

Set up a CI/CD pipeline so that a DAG change made by any engineer is automatically validated and deployed without anyone manually touching the production server.

How to structure the answer: PR opened → CI runs lint + `airflow dags list-import-errors` against the changed files → PR merged to main only if that passes → git-sync (already running as a sidecar against the DAGs repo) picks up the new commit within its poll interval → Scheduler re-parses and the new/updated DAG appears in the UI. No manual deployment step anywhere in that chain.

BUSINESS / CLIENT CASE

CLIENT SAYS

"Only one engineer knows how to deploy DAG changes — he manually copies files onto the server — and when he's on leave, nothing can be updated or fixed."

How you'd respond: This is a classic bus-factor problem with a well-known fix: move DAGs into a Git repository, set up git-sync so the Airflow environment pulls from that repo automatically, and add a lightweight CI check so any engineer's PR is validated before it merges. Now any team member can ship a fix through a normal PR process, deployment is auditable, and the org isn't blocked on one person's availability.

GLOSSARY

DAG
Directed Acyclic Graph — the workflow definition; a set of tasks and their dependencies with no cycles.
DagRun
One execution instance of a DAG for a specific logical_date / data_interval.
TaskInstance
One task, within one specific DagRun — the actual unit of work that gets a state (queued/running/success/failed/skipped).
Operator
A reusable template defining what kind of work a task does (BashOperator, PythonOperator, PostgresOperator...).
Sensor
A special operator that waits for a condition before letting downstream tasks proceed.
Hook
A reusable interface for talking to an external system (e.g. PostgresHook), usually built on top of a Connection.
XCom
"Cross-communication" — small values passed between tasks via the metadata DB.
Executor
Decides where/how tasks physically run — Local, Celery, Kubernetes.
Scheduler
Parses DAGs and decides what should run next, writing that decision to the metadata DB.
Triggerer
Runs deferred/async sensors without occupying a worker slot.
Dataset
A declared data-producing/consuming relationship that lets DAGs trigger on data updates rather than a fixed schedule.
logical_date
The timestamp identifying which interval a DagRun is processing — not the moment it actually executed.

60-SECOND SPOKEN SUMMARY PER MODULE

M1 · ARCHITECTURE

"Airflow orchestrates, it doesn't process. The Scheduler decides what runs and writes that to the Metadata DB, the Executor decides where it runs and hands it to a Worker, the Worker does the actual work and reports back to the DB, and the Webserver just reads that same DB to show the UI. Nothing talks to anything else directly — it all goes through the database."

M2 · DAGs & OPERATORS

"A DAG is the graph, tasks are the nodes, operators are the templates for what a task does. Branching picks one path over another and skips the rest — and anything downstream of a branch needs `trigger_rule=none_failed` or it'll be skipped forever, because skip propagates by default."

M3 · SCHEDULING

"Airflow schedules for a completed interval, so a daily run labeled Jan 1 actually fires at the start of Jan 2 — that's the logical_date gotcha. catchup=True backfills every missed run since start_date the moment you deploy, which is why I always set it explicitly. Datasets let a DAG trigger off data landing instead of a blind time-based guess."

M4 · UI, CLI & MONITORING

"Grid for history, Graph for one run's structure, Gantt for finding bottlenecks. Clear re-runs a task, Mark Success just changes the recorded state without running anything — I'd never use Mark Success to make a failure disappear without knowing why it failed first."

M5 · XCOM, VARS & TEMPLATING

"XCom passes small values through the metadata DB — never a dataframe, that bloats the database. Variables are global config, Connections are credentials, and in production both should be backed by a real secrets manager, not hardcoded in the DAG file."

M6 · CI/CD & DAGSTER

"DAGs deploy via git-sync pulling from a repo, with a CI step that catches import errors before merge — so a broken DAG never silently disappears from the UI in production. Dagster's the asset-centric alternative to Airflow's task-centric model; which one's right depends on how the team thinks about their pipelines, not which is 'newer'."
